# Feature Flag Inventory

Generated by system-wide audit (Phase 5, 2026-06-29). Classifies every env-gated
feature as either:
- **(A) App-only gate** — on-chain code is production-ready; only the off-chain
  layer is disabled. Enabling the flag activates the feature without a program
  upgrade.
- **(B) Requires program changes** — the on-chain instruction shape, CPI, or
  account model is incomplete or incompatible. Enabling the flag before the
  program upgrade will produce broken transactions or silent failures.

---

## Solana / Edge Function Flags

### `VITE_NAVE_BOOTSTRAP_DEPLOYED` (default: `false`)
**Classification: (B) Requires program changes**

Controls whether the one-time founder bootstrap path is exposed in the DAO
creation wizard. The wizard can propose an immediate first deployment (zero
review window) that auto-executes on OversightApproved.

**Why program changes are needed:**
- `nave_execution::create_execution_request` gained a new `bootstrap: bool` arg
  and two additional accounts (`nave_core_program`, `execution_program`) for the
  `record_bootstrap_usage` CPI.
- `nave_core::record_bootstrap_usage` is a new instruction that flips the
  `dao_registry.bootstrap_used` one-time latch.
- The existing deployed programs do NOT have these. Sending the new instruction
  shape against the current program will fail.

**Enable when:** Both `nave_execution` and `nave_core` have been re-deployed
with the bootstrap instructions. After upgrade, set `VITE_NAVE_BOOTSTRAP_DEPLOYED=true`
in both Vercel env and the signer service if applicable.

**Current status:** Programs NOT upgraded. Flag must remain `false`.

### `VITE_NAVE_MARGINFI_ENABLED` (default: `false`)
**Classification: (B→A, partially) — `nave_core` CPI now ships; the governance/adapter path is still (B)**

Controls whether MarginFi appears in the selectable strategy protocol list for
new DAO constitutions (`SELECTABLE_SOLANA_PROTOCOLS`).

**UPDATE (2026-07-01):** `nave_core` now has real `marginfi_deposit` /
`marginfi_withdraw` CPI plus a one-time founder `configure_marginfi_position`
setup instruction (provisions the DAO's MarginFi ledger). Live-verified on
devnet: deposit succeeds unconditionally; withdraw is blocked only by devnet
MarginFi's stale third-party price oracles (an environment limitation, not a
code issue — the health-check remaining-accounts plumbing itself is proven
correct up to that point). These are wired end-to-end at the **app** layer:
- `src/lib/transactionBuilders.ts` → `buildConfigureMarginfiPosition` (founder,
  invoked from the Assets.tsx "configure strategy targets" flow).
- `signer-service` → `handleMarginfiCpi` (operational agent; reachable
  directly via `/sign` or through `bundle_rebalance`), mirroring exactly how
  Kamino's standalone `kamino_deposit`/`kamino_withdraw` are wired.

**Remaining gap (why the flag stays `false`):**
- `nave_marginfi_adapter` (deployed at `Gavh8GezswR14BYC851r6vevk267iWDfBkC3Fo49b1q7`)
  — the target of the GOVERNANCE-approved `execute_strategy` path — was **not**
  touched by this fix (a separate deployed program; out of this app repo's
  scope) and still only validates escrow bookkeeping. A DAO that approves a
  MarginFi allocation via a normal governance proposal today would still have
  funds land in escrow and sit idle, exactly as before.
- The flag gates BOTH surfaces (constitution selectability for governance
  proposals, and the Assets.tsx protocol dropdown), so it stays `false` until
  the governance path is also closed — enabling it today would let a DAO
  select MarginFi in its constitution believing governance-approved
  allocations work, when only the standalone operational-agent path does.

**Enable when:** `nave_marginfi_adapter` (or `nave_execution`'s `execute_strategy`
dispatch) is updated to CPI into the new `nave_core` instructions instead of
just validating escrow bookkeeping — a contracts-repo follow-up.

**Current status:** `nave_core` CPI shipped and live-verified on devnet;
adapter/governance path still a dead end. Flag remains `false`.

### `NAVE_SWAP_ENABLED` (signer service, default: `false`)
**Classification: (A) App-only gate (mainnet only)**

Enables the `jupiter_swap` action in the signer service, which fetches a Jupiter
aggregator swap route off-chain and submits it through the agent keypair's ATAs.

**On-chain status:**
- `nave_core::jupiter_swap` exists in the deployed program (but is a mainnet-only
  exercisable path — Jupiter v6 is NOT deployed on devnet).
- On devnet, calling this action will CPI a non-existent program and fail.
- The signer's `SWAP_ENABLED` gate prevents any swap action from reaching the chain.

**Enable when:** Deployed on mainnet AND `NAVE_SWAP_ENABLED=true` is set in the
signer service env AND `VITE_SWAP_ENABLED=true` (or equivalent) in Vercel.

**Limitations:**
- This swaps via the AGENT KEYPAIR's own ATAs, not directly from the
  `vault_authority` PDA. It cannot be used for vault→vault swaps without an
  on-chain swap CPI in `nave_core`.
- `NAVE_SWAP_MAX_SLIPPAGE_BPS` (default 1000 = 10%) caps per-swap slippage.

**Current status:** Mainnet-only; disabled on devnet. Flag `false` everywhere. ✓

### `NAVE_AUTO_WITHDRAW_ENABLED` (orchestrator, default: `false`)
**Classification: (A) App-only gate: on-chain code is ready**

After a strategy request reaches `Executed` status and a delay of
`NAVE_WITHDRAW_DELAY_SECS` (default 3600s = 1h) has elapsed, the orchestrator
automatically calls `withdraw_from_strategy` to pull principal back to the
treasury vault.

**On-chain status:** `nave_execution::withdraw_from_strategy` is fully deployed
and tested. No program changes needed.

**Enable when:** Operators want automatic post-execution principal withdrawal.
Note: `NAVE_COMPOUND_ENABLED` (below) takes precedence over `AUTO_WITHDRAW` when
both are enabled — compound harvests the yield gain only, leaving principal deployed;
auto-withdraw pulls the full amount.

**Current status:** Disabled. Can be enabled without program changes. ✓

---

### `NAVE_COMPOUND_ENABLED` (orchestrator, default: `false`)
**Classification: (A) App-only gate: on-chain code is ready**

After execution, the orchestrator reads the `StrategyPosition.current_value`
vs `deposited_amount` to detect realized yield, then harvests only the gain via
`withdraw_from_strategy(gain)`, leaving principal deployed. The harvested gain
re-enters the governance pipeline (planner → proposal → vote → redeploy).

**On-chain status:** Uses the existing `withdraw_from_strategy` and position
oracle accounting. No program changes needed.

**Enable when:** Ready to activate yield compounding. Requires:
- `NAVE_COMPOUND_ENABLED=true`
- `NAVE_COMPOUND_MIN_GAIN_BPS` (default 100 = 1%) — min gain threshold
- `NAVE_WITHDRAW_DELAY_SECS` as the compound cooldown

EVM `withdraw_from_strategy` harvest and auto-withdraw calls pass a positive `min_out`: `amount * (10_000 - 50) / 10_000`, and at least 1. That is the same 50 bps bound as `NaveConstants.DEPOSIT_SLIPPAGE_BPS` and the signer `withDefaultMinOut`. The harvest amount is realized gain only, so principal stays deployed. Founder withdrawals still quote through `resolveEvmMinOut`.

**Current status:** Disabled. Can be enabled without program changes. ✓

### `NAVE_POSITION_ORACLE_ENABLED` (orchestrator, default: `true`)
**Classification: (A) App-only gate: on-chain code is ready**

Enables periodic `update_strategy_position_value` calls after each execution,
refreshing the on-chain `StrategyPosition.current_value` to reflect accrued yield.
This feeds the compound harvest math and NAV accuracy.

**Current status:** ENABLED by default. Leave enabled unless debugging. ✓

---

### `JITO_BUNDLE_REBALANCE_ENABLED` (orchestrator, default: `true`)
**Classification: (A) App-only gate: enabled by default**

When multiple direct-CPI operations (e.g., `jupiter_deposit`) become ready in
the same poll cycle for the same DAO, the orchestrator submits them atomically
as a Jito bundle (≤4 ops) instead of sequential signer calls. Falls back to
sequential submission on devnet or when bundles are unsupported.

**Current status:** ENABLED by default. On devnet the signer auto-falls-back to
sequential submission. ✓

---

### `VITE_ESCROW_PDA_ENABLED` (default: `true`)
**Classification: (A) App-only gate: on-chain code is ready**

Controls whether the `strategy_escrow` PDA (a separate vault per protocol) is
used for capital staging, vs the legacy path where adapters required
`strategy_escrow == vault_token_account`.

Both paths exist on-chain. The PDA-escrow path is the correct default for all
new deployments. The `false` path is a legacy fallback for any deployment where
adapters were deployed without the escrow change.

**Current status:** TRUE (correct default). ✓ Set `NAVE_ESCROW_PDA_ENABLED=true`
in signer service to keep in sync with the VITE flag.

## GenLayer review gates (default off)

These three flags are read only when the env value is the literal `true`. Unset is off. They sit in `evaluateGuardrails`, in front of both the Solana signer path and the EVM relay path. Full boundary: [`GENLAYER.md`](GENLAYER.md).

### `NAVE_GENLAYER_GATE` (default: `false`)
**Classification: (A) App-only gate**

When on, a signing role needs a finished charter pass whose action hash matches the execution request. A missing, unfinished, or failed review blocks. A pass does not create a transfer. The vault, the caps, and the payload binding stay on the treasury chain.

**Enable when:** `NAVE_GENLAYER_CHARTER_ADDRESS` points at a deployed `CharterAdjudicator`, and the same check has been exercised across all five supported testnet chains (`solana`, `ethereum` `11155111`, `base` `84532`, `robinhood` `46630`, and `arc` `5042002`).

**Current status:** Off (`NAVE_GENLAYER_GATE=false`). Bradbury serves CharterAdjudicator `0x8F935d913e507A1C8869bcD81803Fef289F1F2B0`, VenueWatch `0xc27B9E337Cc0c277818210c9563A8E5536b2ACe6`, and HaltAppeal `0x7e302d6EbFBCfdf53F8d41F21ffE24401de1B6A4`. All five testnet chains (`solana`, `11155111`, `84532`, `46630`, `5042002`) have been verified end-to-end with live charter and venue reviews on Bradbury. The three gates stay off by default unless explicitly set to `true`. A finalized review does not turn a gate on, and a finished pass does not authorize a transfer.

### `NAVE_GENLAYER_VENUE_GATE` (default: `false`)
**Classification: (A) App-only gate**

When on, a finished venue status of `stop` withholds a new deploy into that venue. `fine` and `watch` do not. Changing the on-chain allowlist still takes a governance vote on the treasury chain. `genlayer-venue-watch` warms venue reviews across all five testnet chains (`solana` `jito`/`kamino`, `ethereum` `aave-v3`/`compound-v3`, `base` `aave-v3`, `robinhood` `morpho-steakhouse-usdg`, and `arc` `morpho-steakhouse-usdc`).

**Enable when:** `NAVE_GENLAYER_VENUE_ADDRESS` is set and each venue has a real `https` status or security page.

### `NAVE_GENLAYER_HALT_GATE` (default: `false`)
**Classification: (A) App-only gate**

When on, a finished `keep_pause` blocks `clear_halt`. `lift_pause` does not sign `operational_clear` and does not shorten the review window. The Oversight key (role `operational`) on the treasury chain is still required to lift a pause.

**Halt recovery (`clear_halt`) flow:**
- **Autonomous Oversight recovery (`operationalGate`)**: When an execution request is `Halted` on-chain, the Oversight agent (`agent_role = "operational"`) evaluates whether the halt remains warranted (`haltPrompt.ts`). If the halt was recorded with deterministic causes (`openHaltCauses`), every recorded cause must now pass. If the halt was a model-only halt (`openHaltCauses: []`), `operationalGate` permits `clear_halt` once all deterministic guardrail checks and active GenLayer gates pass. The orchestrator then relays `operational_clear` on-chain (`NaveExecution.operationalClear` on EVM or `nave_execution::operational_clear` on Solana), moving the request back to `InReview`.
- **Founder-signed recovery (`agent-admin` `clear_halt`)**: A DAO founder can also clear an on-chain halt directly by signing `nave-admin|<dao_address>|clear_halt|<execution_request_address_or_index>|<unix_ms>` with their founder wallet and calling `agent-admin` with `action: "clear_halt"`, which verifies on-chain founder authority and relays `operational_clear`.

**Enable when:** `NAVE_GENLAYER_HALT_ADDRESS` is set.

## How to Enable a Flag Safely

1. Check the Classification column above.
2. If **(B) Requires program changes**: complete the on-chain work first, upgrade
   the program, run tests, then flip the flag.
3. If **(A) App-only gate**: set the env var in the appropriate runtime
   (Vercel for `VITE_*`, Railway for signer, Supabase Secrets for edge functions)
   and redeploy/restart.
4. After enabling, run the devnet E2E suite (`npm run verify:agentic-e2e-suite`)
   to confirm no regressions.
